# One application model: Services, Deps, a Switch, a Door; no runtime dependency graph

Every application is written the same way. A Service is a module with a fixed shape (`type t`, `config`, `deps`, `error`, `create ~sw config deps`, `status`). A Program acquires Services in dependency order in a `let*` chain inside one Eio Switch, which releases them in reverse. The Door (`Eta_app.run`) builds Env, decodes Config through the config type's derived codec (ADR-0008), installs signal handling, runs the Program, renders the full Cause on failure, and returns the exit code. Status is read from the real values. This is the direct-style equivalent of TypeScript Effect's services and layers with the graph resolved by the compiler instead of at runtime. v1's `eta_component` reproduced the layer graph dynamically and, in Pie, became a shadow of the real data path within a month (capabilities in `Obj.t` refs, supervision retrying a dummy graph, fabricated health); Pie deleted it and converged on exactly this model. A runtime-checked dependency graph is therefore rejected, not postponed.
